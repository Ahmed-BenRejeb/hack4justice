# CLAUDE.md - api/ (Python backend)

Local rules for `api/`. Read the root `CLAUDE.md` first; this file only adds what is specific to this directory.

## Stack

FastAPI, SQLAlchemy 2.0, Alembic, PostgreSQL with pgvector. Dependencies and the virtualenv are managed by `uv` (`pyproject.toml` / `uv.lock`). Python is pinned to 3.12 (`.python-version`), not the latest 3.14 release named in `docs/decision-log.md` D-010: on the day this was scaffolded, several core dependencies (psycopg, pgvector, SQLAlchemy) either had no 3.14 wheels yet or were unverified against it, and a hackathon build cannot spend time on ecosystem breakage. Revisit once those wheels catch up.

## Local setup

0. System OCR dependencies (not managed by `uv`, since they are not Python packages): `tesseract` with the `fra` and `ara` language packs, and `poppler-utils` (`pdftoppm`/`pdfinfo`, used by `pdf2image`). On Arch: `sudo pacman -S tesseract tesseract-data-fra tesseract-data-ara poppler`. Verify with `tesseract --list-langs`; `fra` and `ara` must both be listed.
1. `docker compose up -d db` (repo root) starts PostgreSQL with pgvector on host port 5432. If a local Postgres already holds that port, set `CHAHED_DB_PORT` (for example `55432`) in a git-ignored root `.env` and use the same port in `DATABASE_URL` (D-025).
2. `cp api/.env.example api/.env`, fill `DATABASE_URL` (matches the compose service: `postgresql+psycopg://chahed:chahed_dev_only@localhost:5432/chahed`), `OPENROUTER_API_KEY` and `OPENROUTER_MODEL_ID`. All three are required; the process (and the test suite) will not start without them.
3. `uv run alembic upgrade head` applies migrations.
4. `uv run uvicorn app.main:app --reload` runs the dev server.
5. `uv run pytest` runs the test suite. Tests need the database from step 1 running; each test recreates the schema (`tests/conftest.py`).
6. `uv run ruff check .` / `uv run ruff format .` lint and format.

## Conventions

- `app/config.py` is the only module that reads `os.environ` (root rule). It also loads `api/.env` via `python-dotenv`, so no other module needs to.
- `migrations/versions/` and `migrations/env.py`'s Alembic-generated boilerplate are excluded from ruff (see `pyproject.toml`); do not hand-format them to match the rest of the codebase.
- `app/db/models.py` mirrors `docs/architecture.md` section 4 table for table. A change to one without the other is a bug.
- New feature packages (`extraction/`, `corpus/`, `rules/`, `counterparty/`, `export/`) land only when there is real, tested logic to put in them, per the root rule against placeholder modules.
- `app/rules/registry.py` loads rule definitions (JSON files, one per rule) from the root `rules/` directory into the `rule` table, rejecting any with an incomplete citation. There is no `POST /rules` HTTP endpoint: rule management is a seed/migration-time operation until admin auth exists, per the cut list in `docs/plan.md` section 9. Rule definition files themselves are not authored by a model: a citation only goes in `rules/` once a person has verified it against the official text and promoted it to `verified` in `docs/facts.md`.
- `app/extraction/ocr.py` extracts text: born-digital PDFs are read via their text layer (`pypdf`), scanned PDFs and images fall back to OCR (`pdf2image` + `pytesseract`, languages `fra+ara+eng`). `app/extraction/service.py` wires this into upload: it writes one `extraction` row (`field_name="full_text"`) and sets `document.status` to `"extracted"` or `"extraction_failed"`. Field-level extraction (parties, tax ids, amounts) is not built yet: it needs real hero documents to validate against (`fixtures/hero/` is still empty), per Phase 2's own gate in `docs/plan.md` section 8.
- `app/providers/embeddings.py` is the sole embeddings provider (D-012, now resolved rather than assumed): local `sentence-transformers`, model `paraphrase-multilingual-MiniLM-L12-v2`, 384 dimensions, matching `EMBEDDING_DIMENSIONS_DEFAULT`. `torch` is CPU-only, pinned via `[tool.uv.sources]` in `pyproject.toml` to `https://download.pytorch.org/whl/cpu` (the default PyPI `torch` wheel pulls ~2GB of CUDA/nvidia packages even with no GPU; do not remove that source override). OpenRouter's own `/api/v1/embeddings` endpoint was verified live and does work, but the default stays local per the team's choice, recorded in `docs/decision-log.md` D-018.
- `app/corpus/chunking.py` splits PDF pages into citable pieces, article > paragraph (`I`, `II bis`) > item (`a)`, `b bis)`, `1-`) > dashed item (`tiret N`), read from line-start markers only, so it stays content-agnostic (D-031). Article headings accept `Article N`, `Article N.-` (D-021) and `ARTICLE N :` (D-026). A piece over `CORPUS_CHUNK_MAX_TOKENS` (450, `app/config.py`) is split by sentence with one sentence of overlap. Each chunk keeps its PDF page and character offsets. `app/corpus/service.py` embeds `heading_path + text` and upserts on (source, article, paragraph, offset), deleting chunks the source no longer produces, so chunk ids survive a re-index. `app/corpus/load_corpus.py` reads `corpus/sources/manifest.json` (PDF file, page range, provenance) and indexes each source; the compose `api` command runs it after `load_rules`. `app/corpus/retrieval.py` is hybrid (D-035): a pgvector cosine search (candidates below `RETRIEVAL_MIN_SIMILARITY` dropped; no vector index, not needed below about 10,000 chunks) and a French full-text search over `text_search`, a column generated with the `chahed_french` configuration (French stemming after `unaccent`, created by migration `b5d8e2a4c617`; query terms of at least `TEXT_QUERY_MIN_LEXEME_CHARS` characters are ORed, D-037), fused by reciprocal rank. `search()` returns `Hit`s saying which search found each chunk; it ranks the whole corpus unless `verified_only=True`, which ranks verified chunks only (D-037). `excerpts()` wraps matched terms in `\x02`/`\x03` via `ts_headline`. Tests create the `unaccent` extension and the `chahed_french` configuration in `conftest.py`, because they build tables from the models, not the migrations (D-036).
- `app/api/v1/corpus.py` serves the corpus (D-036): `GET /corpus/search`, `/corpus/chunks/{id}`, `/corpus/sources`, `/corpus/verification-queue`, and `GET /findings/{id}/related` (`app/corpus/related.py`: the query is the rule's verbatim citation plus the missing fact; a passage whose text or 40+ character opening sentence already appears in the citation is left out). Passage response models require `verified_by`/`verified_on`, so an unverified chunk cannot serialize; an unverified chunk id answers 404 like a missing one; the queue returns references only. `tests/test_corpus_api.py` asserts unverified text never appears in any response. Wire types are in `web/lib/api-types.ts`. `app/providers/embeddings.py`'s `count_tokens` counts with the embedding model's own tokenizer.
- `app/corpus/verification.py` applies the tracked register `corpus/verified-passages.json` (path: `VERIFIED_PASSAGES_PATH`, copied to `/verified-passages.json` in Docker) at the end of every `load_corpus` run: a chunk is `verified` only while an entry matches its source PDF sha256, article, paragraph and text sha256; everything else is reset to `unverified`, and entries matching nothing are printed, not dropped silently (D-032). An entry without `checked_by` fails the load. To add one, a person runs `uv run python -m app.corpus.verification "Article 52" "I, a)"`, compares the printed text with the official page it links, and pastes the printed entry with their name and date. Never add an entry for text you have not read on the official page yourself; a model never adds one. `tests/test_verification.py` checks that every real register entry matches the real corpus.
- `app/corpus/evaluation.py` measures retrieval on `corpus/eval/questions.json` (format in its docstring): recall@5, mean reciprocal rank, and verified coverage (the share of expected passages a person has verified), ranking the whole corpus so the score reflects retrieval alone (D-033). `uv run python -m app.corpus.evaluation` prints misses and passages awaiting verification, and exits 0 only when recall meets `RETRIEVAL_RECALL_TARGET` (0.9, `app/config.py`). Team members write the question set, a model never does; until it exists, the CLI reports the target not met and `tests/test_retrieval_eval.py`'s real-set test is skipped with that reason.
- `app/rules/engine.py` is the deterministic dispatcher: given a `Rule` and a facts dict, it imports `rule.logic_ref`, calls it, and expects back a `Decision(code=...)` or an `Abstention(missing_fact=...)` (anything else raises `TypeError`). It records the `Finding` and its `Citation`.
- `app/rules/cirppis_art52_honoraires.py` is the first real (non-fixture) rule logic module, an assisted rule against the real Article 52 text sourced in `corpus/sources/` (D-021): it asks the model (live OpenRouter call, `extract_fact`) whether a document describes an Article 52(I)(a) category (honoraires, commissions, courtages, loyers), abstaining if it cannot tell, then deterministically checks (no model call) whether the text also mentions withholding at all. It never computes or asserts a rate: Article 52's rates carry many amended exceptions, and guessing one would violate the root CLAUDE.md design law. Tested live against the real model. Registered as `rules/cirppis-art52-i-a.json` (code `CIRPPIS-ART52-I-A`) after a person on the team checked the citation against the DGI's 2026 edition and promoted it to `verified` in `docs/facts.md` (D-026). Being assisted, it makes one live OpenRouter call per uploaded document. `tests/test_rules_registry.py` checks that every file in `rules/` loads and that its `logic_ref` imports.
- `app/rules/withholding_code_proposal.py` builds `docs/plan.md` section 2's "technical core": propose the real DGI TEJ withholding code among the 36 in `schemas/tej/TEJRSCodesOperations_v1.0.xsd` (D-019). Deliberately scoped to one family only (RS2_000001 vs RS2_000002, honoraires/commissions/courtages, distinguished by the beneficiary's fiscal regime); every other code family (loyers, capitaux mobiliers, cessions, and so on) abstains by name, not modeled yet. Tested live against the real model. Not yet a registered rule: no JSON definition exists under `rules/` for it yet.
- **Important finding (D-027):** `docs/plan.md`'s anchor case names "Article 62" as the governing article, but the real Article 62 in the Code de l'IRPP et de l'IS governs bookkeeping/accounting record obligations, not withholding certificates or code selection - it does not match the anchor case. Real candidates found instead: Article 52(I)(a) (rate/category basis, now the verified, registered rule above) and Article 55(I) (the certificate-delivery obligation, which names an electronic platform almost certainly the TEJ system). This is a correction to the pitch's central citation, not an engineering change; see `docs/facts.md` and `docs/decision-log.md` D-027 before "Article 62" reaches a slide.
- `app/rules/service.py`'s `evaluate_all_rules()` is now wired into `POST /documents` (after a successful extraction): it builds a facts dict from the document's `Extraction` rows and runs every registered `Rule` against it. With an empty registry this is a real no-op, not a stub. `GET /documents/{id}/findings` resolves each finding's citation. Caught a real bug while wiring this: `SessionLocal` is `autoflush=False`, so the `Extraction` row `run_extraction()` adds was invisible to the very next query unless flushed first; `run_extraction()` now flushes explicitly. Watch for the same class of bug anywhere a query follows an `add()` without a flush or commit in between.
- `app/api/v1/officer.py` implements the queue and decisions. The queue's current definition (`document.status == "extracted"` with no `officer_decision` yet) is still a placeholder for "pre-qualified": rules now run automatically, but with an empty registry there is nothing to qualify against yet.
- `app/export/xsd.py` validates an XML document against an XSD schema; the generic mechanism is still tested against the small fixture schema in `tests/test_xsd.py`.
- `app/export/tej.py` generates a real DGI TEJ "DeclarationsRS" (withholding declaration) and validates it against the real schema at `schemas/tej/` (see `schemas/tej/SOURCE.md` for provenance and D-019). That schema was found and downloaded from the DGI's own `jibaya.tn` portal, not guessed. `schemas/tej/TEJISOPaysDevises.xsd` has one line removed versus the official download: the published file is not well-formed XML (a stray duplicate `</xs:enumeration>` at line 1580); `schemas/tej/original/` keeps the untouched download. The withholding code count found this way (36, not "more than 40") is a candidate for `docs/facts.md`, not yet `verified` - that promotion is still a human step.
- `app/providers/openrouter.py` is the sole chat-completion provider (`complete()` for free text, `extract_fact()` for the assisted-rule case: a JSON `{value, confidence}` answer, `None`/low confidence when the context does not contain the answer). Reads `OPENROUTER_API_KEY` and `OPENROUTER_MODEL_ID` from `app/config.py`, both required with no default; `app/config.py`'s `Settings` now requires them too, so the whole process needs them set to start, matching how `DATABASE_URL` is already required. Tested live against the real API (small real cost per test run), not mocked: free-text instruction-following is not perfectly reliable even for trivial prompts (observed "Fruit" instead of "banana" for an identical prompt across two calls), so only the structured JSON path is asserted on exact content; the free-text test only asserts a non-empty reply comes back.
- `app/counterparty/` does not exist. Re-checked 2026-09-12 from a different network: `www.registre-entreprises.tn/rne-public` now loads (a real Angular portal), and its own served JS names a real search endpoint, `GET /api/rne-api/front-office/entites`, with real parameters (`idUnique`, `denomination`, `nomCommercialFr`, `cnssNumPM`, others). Called live, unauthenticated: `401 Access is denied`; the OAuth flow at `/api/rne-auth-api/oauth/token` needs a real registered user account, not a self-serve key. See `docs/facts.md` and D-020. Revisit once the team has decided whether to obtain a real account (a real-world action, not an engineering one).
- `app/api/v1/export.py` implements `POST /documents/{id}/export`: only after an `officer_decision` with `action == "validated"` exists (409 otherwise), and only with a full, caller-supplied set of TEJ fields (declarant, beneficiaire, one or more operations) - nothing is inferred from the document or defaulted, since field-level extraction does not exist yet. A schema-invalid payload returns 422 with the real `lxml` error list and persists nothing.
- `app/api/v1/organisations.py` lists organisations and creates MSMEs (409 on a duplicate `tax_id`). It exists because there is no auth yet: the web upload screen picks or creates the organisation a document is filed for (D-024).
- `document.filename` keeps the uploaded name (base name only) next to `storage_ref`; migration `a3f9c2d17b64` backfills older rows from `storage_ref`. `GET /documents/{id}` also returns the organisation, the officer decision and the latest export, and `GET /officer/queue` rows carry filename, organisation name and decided/abstained finding counts, so the web screens need one request each (D-024).
- `app/export/codes.py` reads the withholding operation codes and their descriptions from the real `TEJRSCodesOperations_v1.0.xsd`, served by `GET /export/operation-codes`: the export form offers exactly the codes the validator accepts.
- `tests/conftest.py` looks for Liberation Sans at the Arch path, then the Debian/Ubuntu path, so the suite runs on either.

## Docker

`docker compose build api` builds the image (`api/Dockerfile`, plain `pip install uv` on `python-slim`; the `ghcr.io/astral-sh/uv` base image is unreachable from this network, denied on pull). The image also installs `tesseract-ocr`, `tesseract-ocr-fra`, `tesseract-ocr-ara` and `poppler-utils` via apt, matching the local setup requirement above, and pre-downloads the local embedding model during build (`RUN uv run python -c "from app.providers.embeddings import _model; _model()"`) so the container never needs Hugging Face access at runtime, only at build time. `docker compose up` runs `db` and `api` together: the `api` container runs `alembic upgrade head` before starting uvicorn, so a fresh volume self-migrates. `docker compose up` also builds and starts `web` (`web/Dockerfile`), which reaches the API at `http://api:8000` inside the compose network. `api`'s `DATABASE_URL` inside compose points at the `db` service hostname, not `localhost`. `OPENROUTER_API_KEY`/`OPENROUTER_MODEL_ID` come from `api/.env` via `env_file:` in `docker-compose.yml`; without a real `api/.env`, the container fails to start (the whole process requires them, same as `DATABASE_URL`).

The build context is the repo root, not `api/` (`docker-compose.yml`'s `api.build: {context: ., dockerfile: api/Dockerfile}`), because the image needs the repo-root `schemas/` directory: it is copied to `/schemas` and `SCHEMAS_DIR=/schemas` is set accordingly, consumed by `app/config.py`. This fixed a real bug: `app/export/tej.py` used to locate the schema via `Path(__file__).resolve().parents[3]`, correct only for the host's directory depth, not the container's (`WORKDIR /app` with `api/`'s contents copied directly into it) - the export endpoint 500'd in the container with a missing-file `OSError` until both the path logic (now `settings.schemas_dir`) and the build context were fixed. Verified by rebuilding the image and re-running the full upload-to-export flow against the live container. `.dockerignore` lives at the repo root now, matching the new context. `corpus/sources/` is copied to `/corpus-sources/` the same way (`CORPUS_SOURCES_DIR=/corpus-sources`); `rules/` is copied to `/rules/` the same way (`RULES_DIR=/rules`), and the compose `api` command runs `load_rules` between `alembic upgrade head` and uvicorn, so the registry is refreshed on every start. `load_rules` upserts by code, so repeating it is safe; deleting a rule file does not remove its row (D-026).
